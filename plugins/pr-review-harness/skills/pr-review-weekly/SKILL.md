# レビュー知見の週次運用（配信・投票・反映）

抽出スキル `/pr-review-extract` が決定式で選んだ候補を**人間の投票**で最終決定し、結果を台帳へ書き戻す。毎週月曜にローカルで実行する想定。**実行のたびにスキル自身も見直す**（手順7）。

**チームで共有するのは Slack へ出す投稿だけ**で、リポジトリに台帳は置かない。実行者のローカルにある `~/.claude/pr-review-learnings/pr-review-learnings.json` は作業場であり、レビューコメントの引用を含むので共有しない。

## 位置づけ

- 抽出の3レイヤー（事実 → 判断 → 決定）の先にある「**執行**」を担う。このスキル自身は新しい判断をしない（不採択候補の再割り振りを除く）
- 重要度の判定は投票（人間）に委ねる。スキルは票を数えて執行するだけ
- 採用側の反映状態は手動管理しない: 反映PRがマージされれば、次回の増分実行のギャップ分析が「反映済み」に倒す
- **投票の記録は Slack チャンネルが正。** 台帳 json の `vote` は追記専用のキャッシュで、チャンネルを読めば再構成できる。こうしておくと、どのマシンから実行しても・クラウドから実行しても集計が成立する

## 引数

- channel: **必須**。配信・集計先の Slack チャンネル（ハードコードしない）
- `--period`: 対象週を明示する。指定すると先週の自動算出（手順3）を行わない。実行が飛んだ週を後から埋めるときに使う
- `--dry-run`: 集計結果と投稿予定の内容を表示するだけで、Slack 投稿・PR作成をしない。なお `--dry-run` でなくても配信前のプレビュー確認は必須（手順4）

## 手順

### 1. 先週の投票を集計する

**未決着の候補は Slack チャンネルを読んで特定する。** 台帳 json の `vote.message_ts` は補助であって前提にしない — 実行環境が変わると（クラウド実行・別マシン）ローカルの状態ファイルを持ち越せず、ts に依存すると集計そのものが不能になる。チャンネルには投稿が残っているので、そちらを正とする。

- **集計対象は「まだ決着していない配信分」。** 期間で切らない。チャンネルを新しい順に読み、**最新の `[レビュー知見サマリ]` 投稿より後に配信された候補投稿**をすべて拾う。各実行はサマリを1つ出してから候補を並べるので、この範囲がちょうど前回配信して未集計のぶんになる。実行が飛んだ週があっても、決着しないまま残っている候補を取りこぼさない
- 拾う対象は**本文のどこかに** `[レビュー知見 ...]` を含む投稿のうち（太字記号 `*` の有無・行の位置は問わない。手で書き足した投稿は目印が末尾にあることもある）、`[レビュー知見サマリ]`（週の記録）と `[レビュー知見 見送り]`（候補にしなかったものの一覧）を除いたもの。見出しは連番ではなく内容を表す語なので、パターンで絞らずこの2つを除外する形で判定する
- 各投稿の**本文に含まれる `comment_url`** を控える。元のレビューコメントに辿れる唯一の恒久キーで、反映PRの根拠にも、再発の照合にも使う
- 各候補投稿のリアクションを取得し、リアクションしたユニークユーザー数を数える（下記「投票ルール」のとおり、絵文字の種類は問わず配信者の先押しも1票）
- **スレッドに返信があれば必ず読む。** 明示的な反対（「ルール化しないでほしい」「今回は見送ろう」等）で決着していたら、**票数にかかわらず採用しない**。不採択として扱い、`fitness_reason` に決着の要点とスレッドへのリンクを書く。リアクションは賛意の表明にすぎず、議論の結論を上書きしない
- **2票以上 かつ スレッドで反対の決着がない → 採用**: `vote` に `outcome: "adopted"`・`votes`・`decided_at` を記録する
- **2票未満 → 不採択**: `outcome: "rejected"` を記録し、fitness を決定木の残り（文脈依存の教訓なら `solutions` / そうでなければ `skip`）で再判定して更新する（`fitness_reason` に不採択の票数と再判定理由を書く）。fitness が変わるので決定式の候補から自然に外れ、翌週の投票に再登場しない。**ただしチャンネルの投稿は消さない** — 別のPRで同じ事象が再発したとき、繰り返しの証拠になる（手順3）
- md の該当エントリに「投票」行（結果・票数・日付）を追記する
- 台帳に該当エントリが無い投稿（別マシンで配信された等）は、`comment_url` から元のレビューコメントを引いてエントリを起こしてから集計する。投稿が消えている候補は再配信対象に戻す

### 2. 採用分の反映PRを作成する

- 同じ投入先はまとめて **1投入先 = 1PR**。**ブランチは `staging` から切る**（作業中のブランチから切ると、無関係な変更を巻き込んだPRになる）。`/create-pr` の慣例（PRテンプレート・日本語・`--body-file`）に従う
- `fitness = rule` → 投入先ファイル（`.claude/rules/` 等）へルールを追記するPR。WHAT / HOW / WHY と Bad/Good 例を数行で。`.claude/rules/` を触ったら AGENTS.md の `@path` 参照行を確認する
- **追記する前に、その知見が上書きする既存の記述を探して同じPRで直す。** 抽出時のギャップ分析で「部分的」と付いたものがそれにあたり、既存の記述が足りなかったから同じ指摘が出ている。隣に新しい行を足さず、置き換えるか統合する。**足すだけの反映は、個々のルールが良くてもリポジトリを悪くする**（常時ロードされるルールは、増えるほど全タスクのコストになる）。
- **`.claude/` 配下は Edit ツールで書き換えない。** 保護対象として権限確認が入り、**無人実行はそこで止まる**。`python3` のヒアドキュメントなど Bash 経由で書けば通る。`AGENTS.md` のようにディレクトリ外のファイルは Edit でよい
- **例に書くコードは、そのリポジトリで実際に使われている書き方に合わせる。** 一般的な Rails の書き方をそのまま置くと、慣例と食い違うルールができる（`flash[:alert]` と書いたが、管理画面は `flash[:danger]` で統一されていた）。書く前に既存コードを grep して多数派を確かめる
- `fitness = automation` → RuboCop カスタムCop / CI / Danger の実装PR（実装が大きければ Issue 起票でも可）。検出は「警告のみ」から始める（危険検出に安全例外を足して黙らせると、本当に危険な変更を通してしまう）
- PR本文に根拠（棚卸しエントリID・元PR・対応コミット・投票結果）へのリンクを含める
- **PRの作成とレビューアーの指定は分ける。** 作成時にレビューアーを渡すと、**指定だけが失敗してもPR本体は作られている**。エラーだけ見てやり直すと同じPRが2本できる。まずレビューアー無しで作り、そのあと指定する
- **実行者のログイン名を最初に引いておく**（`curl -s https://api.github.com/user` の `login`）。誰として動いているかが分からないと、下のフォールバックを事前に判断できない
- **レビューアーには元PRの Author を指定する**。指摘を受けた当事者がルール文の妥当性を一番判断できるため。Author は台帳エントリの `author`（抽出時に記録している）を使い、無ければ `curl -s "https://api.github.com/repos/<repo>/pulls/<n>"` の `user.login` で引く
  - Author が**実行者自身**のときは GitHub が拒否する（`Review cannot be requested from pull request author`）ので、**指摘したレビューアー**にフォールバックする
  - どちらも実行者自身、または退職等で指定できないときは未指定のままにする（PR本文に理由を1行書く）
  - 1投入先に複数エントリをまとめた場合は、各エントリの元PRから重複を除いて全員を指定する

### 3. 増分抽出を実行する

**`--period` の指定があればそれに従う。** 無ければ**実行日から見た先週**（直近の完全な月曜〜日曜・JST）を対象にする。`/pr-review-extract --period 先週` がこの切り方のショートカット。

**「前回処理した週の次の週」にはしない。** 実行が飛ぶと配信が過去に取り残され、数週前のPRについて投票を頼むことになる。指摘した本人が「結構前なのでうろ覚え」となり、内容を判断できる人がいないまま票だけが集まる（実例: 5週前の週を配信したところ、指摘したレビューアーから記憶が薄いと申告が出た）。読まれない週が出るのは損失だが、**古い週を配信して投票が形式だけになるほうが損失が大きい**。

- **実行が飛んだ週は自動では埋めない。** 埋めるなら `--period 2026-08-03..2026-08-09` のように明示して別に実行する（1実行1週の制約はそのまま）
- チャンネルの最新の `[レビュー知見サマリ]` 投稿の対象週が先週の1つ前でなければ、**間に未処理の週がある**。どの週が未処理かをサマリ投稿に1行書き、埋めるかどうかを運用側が決められるようにする。ここでやるのは「書く」ことだけで、勝手に遡らない
- 算出した対象週は、実行の冒頭でログに出す（意図しない週を処理していないか確認できるように）

**1回の実行で進めるのは1週だけ。** 一度に複数週を処理すると fan-out が膨らんで実行が不安定になるため。

決まった対象週で `/pr-review-extract --period <対象週>` を実行する（既定 = チーム全員）。

**抽出結果を、チャンネルの過去の候補投稿と突き合わせる。対象は期間を切らずチャンネル全体。** 同じ事象を指す候補が過去にあれば、**別々のPRでの2回目の観測**として扱う。採用されずに終わった候補でも同じで、票が集まらなかったことは「起きていない」ことの証拠にはならない。

手順1が読むのは未決着の配信分だけなので、**そこで読んだ範囲に頼らない**。再発は数週間から数か月あいて起きるもので、直近だけを見ると救済がほぼ発動しない。

- 走査はヘッダの領域で絞る。今回の指摘と同じ領域の候補投稿を Slack 検索で引き（例: `レビュー知見 ActiveRecord`）、その中だけ本文を開く。全件の本文を読む必要はない
- 突き合わせは `comment_url` ではなくルール案の内容で行う。再発は別のコメントとして現れるので、URLは一致しない
- 2回目と判定したら、`observed_count` を2として抽出側へ渡す。固有性:低でも候補に残る（決定木②）
- 再提案する候補には、**前回の投稿へのリンクと票数を添える**。同じものが再び上がってきた理由を投票する人が判断できるように

### 4. 新しい候補を配信する

投稿する文面は `/pr-review-extract` が `~/.claude/pr-review-learnings/delivery-preview.md` に生成済み。**その文字列をそのまま渡す。** 書式・ヘッダ・装飾記号のルールは抽出スキル側が持っているので、ここで作り直さない。**Slack 記法へ手で直さない** — Slack MCP は渡した文字列を Markdown として解釈して変換するので、先に `*太字*` の形へ直すと斜体になる。

- 配信対象 = `recommended: true` かつ**まだ配信していない**エントリ。既配信かどうかは、手順1で読んだチャンネルの `[レビュー知見 ...]` 投稿に同じ `comment_url` があるかで判定する（台帳の `vote` はキャッシュとしてのみ見る）
- **投稿前にプレビューをユーザーに見せて確認を得る。** 確認できる人間がいない実行形態でこれを省くかどうかは、その運用が決めること（省く場合は実行側の指示で明示する）
- サマリ投稿 → 候補投稿の順に投稿する。候補投稿には `:+1:` を自分で先押しする（ワンタップの投票ボタンを兼ねる。この1票も集計に数える）
- **候補投稿には元PRの Author と指摘したレビューアーへのメンションが入っている**（変換は抽出スキル側で済んでいるので、ここで足さない）。投稿後に「まだチャンネルにいません」と招待を促されたら、その人には通知が届いていない。参加を依頼するか、変換表（`.claude/skills/pr-review-extract/references/github-slack-map.md`）の未対応表へ移す。**無人実行では判断できないので、サマリ投稿のスレッドに誰に届かなかったかを残す**
- 議論は各候補投稿のスレッドで行ってもらう（質問・異議・補足。known-exceptions の材料として次回拾う）
- 最後に**見送り投稿**を出す。チャンネルには `[レビュー知見 見送り] <対象週>` と件数の2行だけを投稿し、**中身はその投稿のスレッドに続けて置く**。候補にしなかったものをチャンネル本流に流すと読まれなくなるため
- **スレッドの各項目にも領域の目印を付ける**（`[ActiveRecord] 参照カラムには外部キー制約を…` のように）。付けないと、見送った指摘が後で再発したときに手順4の走査（領域で絞ったSlack検索）に引っかからず、繰り返しとして数えられない
- 配信した各候補の台帳 json に `vote: { posted_at, channel, message_ts, votes: null, outcome: null }` を追記する（ローカル実行時のキャッシュ。集計はチャンネル側を正とするので、この記録が無くても翌週の集計は成立する）

### 5. 記録を確定する

配信した投稿そのものが今週の記録になる。**リポジトリへのコミットは発生しない**（採用された知見は手順2の反映PRで入る）。ローカルの台帳 json を更新して終わる。

### 7. スキル自体を疑う

**実行が終わったら、使った2つのスキルの記述を振り返る。** この運用は毎週回るので、記述の穴は毎週同じ場所で人を詰まらせる。気づいた回に直さないと、誰も直さない。

次のどれかに当たったら、**スキルの改善案として書き出す**。

- **指示どおりにやると明らかにおかしくなった** — 手順に従うと望ましくない結果になり、判断で外した箇所
- **判断に迷った** — 記述が曖昧で、どちらとも読める箇所
- **書いていないことを自分で決めた** — 手順に無い判断を補った箇所
- **環境の制約で回避が必要だった** — 記述どおりのコマンドや前提が通らなかった箇所

**改善案は、スレッドに書くだけでなくPRにする。** 提案だけ残すと、直す作業が誰かの手番待ちになって溜まる。文章を直すところまでやってしまい、人間はマージするかだけ判断すればよい状態にする。

1. **スレッドに改善案を書く** — サマリ投稿のスレッドへ。配信と同じ場所なので気づいてもらえる。「どのファイルのどの記述を、どう直すか」まで具体的に。指摘だけ残しても次に活きない
2. **スキルを直すPRを作る** — 反映PR（手順2）とは**別PR**にする。混ぜるとルール追記の是非とスキルの直しが同じPRで議論になる
   - ブランチは、**直すスキルが存在するブランチ**から切る。スキルがまだ `staging` にマージされていない間は `staging` から切ると対象ファイルが無い。触ってよいのは `.claude/skills/` 配下だけ
   - **assignee は実行者自身**（このRoutineを動かしているGitHubアカウント）。自分にレビュー依頼はできないので、reviewer ではなく assignee を使う
   - PR本文に、**どの実行で何に詰まったか**（対象週・該当する手順・実際に起きたこと）を書く。数か月後に読んで背景が分かるように
   - スレッドにPRへのリンクを貼って紐づける
3. **直接コミットしない。** `staging` へ直接 push せず、必ずPRにする。全員の挙動が変わる変更なので、マージするかは人間が決める（`.claude/rules/skills.md`）

改善点が無ければPRは作らない。無理にひねり出すと毎週ノイズが出る。

実例: ドライランで「票では採用だがスレッドでは見送りに合意していた候補」を踏み、手順1がリアクション数しか見ていないことが分かった。そのまま本番実行していれば誤って反映PRを作っていた。この振り返りが無ければ、実際に作ってから気づくことになる。

## 投票ルール（サマリ投稿の末尾に足す）

抽出スキルが作るサマリは対象週とスキャンPR数の2行なので、そこへ**先週の投票結果**（採用・不採択の件数と反映PR数）と次の案内を続けて投稿する。しきい値は配信側の運用方針なので、ここが持つ。

- 期限: 次回実行（翌週月曜）まで
- **候補の投稿にリアクション（👍ボタンあり・絵文字は何でも可）= その候補への1票**。配信者の先押し分を含めて2票以上で採用され、ルール追記または機械化の反映PRが作られる
- 質問・異議（「これはルール化しないでほしい」等）・補足は各候補のスレッドへ（known-exceptions の材料として次回拾う）

## 注意

Slack の投稿・リアクション取得は Slack MCP（claude.ai コネクタ）を使う。未認証ならユーザーに接続を依頼して中断する。
