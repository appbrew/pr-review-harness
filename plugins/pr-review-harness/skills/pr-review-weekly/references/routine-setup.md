# Claude Routine で週次運用を自動化する

`/pr-review-weekly` を毎週月曜の朝に自動実行するための設定。Routine は claude.ai 側に作られるもので、
リポジトリにファイルは増えない。**このドキュメントが唯一の再現手段**なので、設定を変えたらここも直す。

## Routine とは何か（ローカルの cron との違い）

| | 挙動 |
|---|---|
| 実行場所 | Anthropic のクラウド。実行者のMacは関係なく、電源が落ちていても動く |
| 環境 | 毎回まっさらな隔離環境。リポジトリを**既定ブランチで** clone して始まる |
| コンテキスト | ゼロ。プロンプトだけが手がかりで、会話の続きではない |
| スケジュール | cron 形式・**UTC**・最短1時間間隔。負荷分散のため数分ずれて起動する |
| 外部接続 | claude.ai の MCP コネクタを紐づけて使う |

## 作る前に必要なこと

**GitHub アカウントの接続。** CLI で `/web-setup` を実行する。成功すると `Connected as <GitHubユーザー名>`
と表示される。未接続のまま作成しようとすると、スキーマの検証にも進まず認証で弾かれる。

```
HTTP 401
Connect your GitHub account before saving a routine that uses a GitHub repository.
```

`/web-setup` はリポジトリを clone する権限を渡すだけで、Claude GitHub App のインストールはしない。
スケジュール実行に必要なのは clone だけなので、**組織オーナーの承認は要らない**（App の導入が要るのは、
GitHub イベントで起動する Routine を作る場合）。

**Routine は作成者の個人アカウントに紐づく。** チームの共有資産ではないので、次の制約がある。

- Slack への投稿もPR作成も**作成者の名義**になる
- 作成者が止めた・トークンが切れた・退職した場合、**週次運用は静かに止まり、チームは気づかない**
- 同僚は claude.ai の管理画面を見られないので、**このドキュメントが唯一の引き継ぎ手段**になる

## クラウドで成立する理由

このスキルはローカルの状態ファイル `~/.claude/pr-review-learnings/pr-review-learnings.json` を
前提にしているが、クラウドセッションはそれを読めない。次で代替する。

| 必要なもの | クラウドでの取得元 |
|---|---|
| 既配信の判定・繰り返しの証拠・処理済みの週 | Slack チャンネルの `[レビュー知見 ...]` 投稿 |
| 反映済みかどうか | `CLAUDE.md` / `.claude/rules/` を grep して毎回導出する |
| 対象のPR | 実行時に `gh` で取得する |

台帳 json をリポジトリに置かないのは、レビューコメントの原文引用を含むため。共有するのは Slack の投稿だけで、
それがそのままクラウド実行の入力を兼ねる。

## 設定値

```
名前         レビュー知見の週次運用
cron         0 22 * * 0        日曜 22:00 UTC = 月曜 7:00 JST
環境         Default
リポジトリ    https://github.com/<owner>/<repo>
モデル        claude-opus-5
MCP          Slack
ツール        Bash / Read / Write / Edit / Glob / Grep / Task
```

**時刻は UTC で書く。** 月曜 7:00 JST は日曜 22:00 UTC なので、cron の曜日は `0`（日曜）になる。
「月曜の朝なのに cron は日曜」で正しい。

**モデルは Opus を使う。** レイヤー2（fitness・固有性の判定）はモデル品質に依存し、
台帳を正解データにした再現テストでも一致率は7割程度にとどまる。ここを軽いモデルに落とすと分類がぶれる。

**ブランチはプロンプトで切り替える。** clone は必ず既定ブランチから始まるので、別のブランチで
動かす必要があるならプロンプトに `git checkout` を書く。設定側にブランチを指定する項目はない。

## プロンプト

クラウドはゼロコンテキストなので、プロンプトだけで完結させる。**運用上の判断（どの週を対象にするか・
繰り返しをどう見るか）もここに持たせる**。手順書側に二重に書くと、変えたときにずれる。
**実物を変えたらこのブロックも同じ内容に更新する。** 逆も同じで、ここだけ直しても実物は変わらない。
実物の書き換えは `/schedule` から `RemoteTrigger` の `update` で行う（`job_config` は部分更新ではなく
まるごと置き換わるので、`environment_id` / `session_context` も一緒に送る）。

**スキルの変更を先にマージしてからプロンプトを合わせる。** clone は既定ブランチから始まるので、
スキルがまだマージされていない状態でプロンプトだけ新しくすると、要約と SKILL.md が食い違い、
上のルールに従って SKILL.md（古い側）が優先される。間に合わないときは、プロンプトの冒頭に
`git fetch origin <ブランチ> && git checkout <ブランチ>` を足して切り替える。

```
<owner>/<repo> のレビュー知見を週次で運用する。あなたはクラウド上の隔離セッションで
動いており、実行者のローカルマシンには一切アクセスできない。

## 最初にすること

`.claude/skills/pr-review-weekly/SKILL.md` と
`.claude/skills/pr-review-extract/SKILL.md` を必ず両方読む（どちらも既定ブランチにある）。
**以下は要約であって、判定基準の正は SKILL.md 側だ。食い違ったら SKILL.md に従う。**

## GitHub の叩き方（この環境固有）

**`gh` CLI は入っていない**。`curl` で REST API を直接叩く。
プロキシが資格情報を注入するので、**認証ヘッダーは不要**（private リポジトリでも 200 が返る）。
SKILL.md の `gh api "repos/$REPO/..."` は
`curl -s "https://api.github.com/repos/<owner>/<repo>/..."` に読み替える。

- **GraphQL は使えない**（拒否される）。SKILL.md は全部 REST で書いてある
- **ページ送りは `page=` を明示して自分で回す**。Link ヘッダーは数値ID形式
  （`repositories/{id}/...`）で、このプロキシはそれを拒否する。Link を辿ると
  1ページ目だけで静かに打ち切られ、取りこぼしに気づけない。
  `per_page=100` で `page=` を 1 から増やし、件数が 100 未満になるまで繰り返す
- PRの作成は MCP の `mcp__github__create_pull_request` を使う（ToolSearch で読み込む）

## 前提

- 配信・集計先の Slack チャンネルは #<配信チャンネル>（channel_id: <CHANNEL_ID>）
- 台帳ファイルは存在しない。既配信の判定・繰り返しの証拠・処理済みの週は、
  すべて Slack の `[レビュー知見 ...]` 投稿から読む
- 反映済みかどうかは CLAUDE.md / .claude/rules/ / docs/solutions/ を grep して毎回導出する
- 目印は角括弧の文字列そのもの。**太字記号 `*` の有無も、行の位置（先頭か末尾か）も問わない**

## やること

1. **投票集計** — 期間で切らない。配信チャンネルを新しい順に読み、**最新の
   `[レビュー知見サマリ]` 投稿より後に配信された候補投稿**をすべて拾う。
   候補投稿とは `[レビュー知見 ...]` を含む投稿のうち、`[レビュー知見サマリ]` と
   `[レビュー知見 見送り]` を除いたもの。
   各候補のリアクションのユニークユーザー数を数える（`+1` と `+1::skin-tone-2` は
   別絵文字として返るのでユーザーIDで重複排除）。
   **スレッドに返信があれば必ず読む。明示的な反対で決着していたら、票数にかかわらず採用しない**
   （リアクションは賛意の表明にすぎず、議論の結論を上書きしない）。
   2票以上かつ反対の決着がなければ採用、2票未満なら不採択。
   **不採択になっても投稿は削除しない**
2. **採用分の反映PRを作成**する。ブランチは必ず `git fetch origin staging` してから
   origin/staging を基点に切る。レビューアーは元PRの Author
3. **増分抽出** — 対象週は**実行日から見た先週**（直近の完全な月曜〜日曜・JST）。
   「前回処理した週の次の週」にはしない（実行が飛ぶと数週前のPRの投票を頼むことになり、
   指摘した本人も内容を覚えていない）。**実行が飛んだ週は自動では埋めない**。
   手順1で見つけたサマリ投稿の対象週が先週の1つ前でなければ、どの週が未処理かを
   サマリ投稿に1行書くだけにして、勝手に遡らない。
   **1回の実行で進めるのは1週だけ**。算出した対象週を最初にログへ出す
4. **繰り返しの検出** — 抽出結果を、**チャンネル全体**の過去の候補投稿と突き合わせる
   （手順1で読んだ範囲に限らない。再発は数週間から数か月あいて起きる）。
   走査はヘッダの領域で絞る（Slack検索で `レビュー知見 ActiveRecord` のように引く）
5. **新候補を配信**する。無人実行なのでプレビュー確認は取らず、そのまま投稿する。
   **候補が0件でもサマリ投稿は必ず行う**
6. **見送り投稿**を出す。`[レビュー知見 見送り] <対象週>` と件数の2行だけを
   投稿し、中身はそのスレッドに置く
7. **スキル自体を疑う**（SKILL.md 手順7）。今回の実行で「指示どおりだとおかしくなった」
   「判断に迷った」「書いていないことを自分で決めた」「環境の制約で回避が必要だった」
   箇所を振り返り、**サマリ投稿のスレッドに改善案を書く**。
   「どのファイルのどの記述を、どう直すか」まで具体的に。指摘だけ残しても次に活きない。
   **スキルを自分で書き換えてコミットしない**。全員の挙動が変わる変更なので人間が判断する。
   改善点が無ければ「無し」と報告すればよい（無理にひねり出さない）

## 投稿の書き方

- 候補のヘッダは `[レビュー知見 <領域>｜<見出し>] <対象週>`。領域は技術領域を表す短い語
  （`ActiveRecord` `セキュリティ` `DB` `管理画面` など）で、**すでにチャンネルで使った語を
  優先して再利用**する。ファイル名や連番は使わない
- **対象週は `YYYY-MM-DD〜YYYY-MM-DD` と両端を省略せずに書く**。週は月や年をまたぐ
- **候補投稿には、元PRの Author と指摘したレビューアーの Slack メンションを入れる。**
  GitHub login → メンバーIDの変換表は
  `.claude/skills/pr-review-extract/references/github-slack-map.md`。
  **表に無い login は推測でメンションせず** `@<login>` の平文で出す（別人に通知が飛ぶと
  通知を切られて投票が集まらなくなる）。サマリ投稿と見送り投稿にはメンションを入れない
- **太字は `**...**` と書く。`*...*` と書かない。** Slack MCP は渡した文字列を Markdown と
  して解釈して Slack 記法へ変換するので、`*太字*` は斜体 `_太字_` に化ける
- **斜体は使わない。** 斜体の記号はアンダースコアで、閉じ記号の直後に全角文字が続くと
  閉じず、記号がそのまま出る（`_ラベル_（補足）`）。太字にはこの制約がない
- 装飾を置くのは行頭のラベルか1行を丸ごと囲む形。文の一部を囲む形は確かめていない
- `.env.dev` や `models.md` のような「ドット＋既知のTLD」は Slack が自動リンク化する

## 制約

- **リポジトリへのコミットはしない**。リポジトリに入るのは手順2の反映PRだけで、
  採用が0件ならPRは1本も作らない
- レビューコメントの引用を含む台帳をリポジトリに置かない
- 迷っても勝手に基準を作らず、SKILL.md に書かれた基準だけで判定する
- 実行の最後に、対象週・スキャンPR数・集計した投票（スレッドの反対で見送ったもの含む）・
  配信した候補数・見送り件数・作ったPR・**スキルの改善案** を箇条書きで報告する
```

## 作り方

CLI で `/schedule` を実行し、上記の設定値とプロンプトを渡す。web から作る場合は
https://claude.ai/code/routines の New routine から同じ内容を入力する。

作成後の管理画面（実行履歴・ログ・一時停止・削除）も https://claude.ai/code/routines。
手元から一覧を見るには `/schedule list`、変更は `/schedule update`、即時実行は `/schedule run`。

## 運用上の注意

- **毎週それなりに重い。** 1 PR = 1 サブエージェントで30件前後を Opus で回す。サブスク枠を消費し、
  1日あたりの実行回数にも上限がある。対象が膨らむときは対象週を短く切る
- **無人実行では投稿前の確認を取らない。** 記法ルール（日本語の文中に `*` `_` を埋めない）は
  プロンプトと SKILL.md の両方に書いてあるが、最終的にチェックする人間はいない。
  投稿がおかしければ Slack 側で消す
- **止まっても通知は来ない。** 実行履歴は https://claude.ai/code/routines から確認する。
  週次の投稿がSlackに現れない週があれば、まずそこを見る
- **緑の完了表示は成功を意味しない。** セッションがインフラエラーなく終了しただけなので、
  何をしたかは実行ログを開いて確かめる
